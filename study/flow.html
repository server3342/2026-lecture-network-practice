요청 한 번 따라가기
curl https://speed.cloudflare.com/…

노트북에서 명령 한 번을 실행할 때 일어나는 일을 순서대로 씁니다. 단계마다 그 단계를 보여 주는 패킷 번호와 시각을 붙였습니다.

측정: 2026-09-29, 세종캠퍼스 Wi-Fi 근거: w04-tcp/out/tcp.pcapng 외 3개 파일

1예시의 조건

이 페이지는 4주차 Task 2의 첫 번째 측정을 예시로 씁니다. 모든 값은 이 저장소의 파일에 있습니다.

시각을 읽는 방법

이 페이지의 시각 t는 캡처의 시각입니다. 첫 SYN을 t = 0으로 합니다. DNS는 SYN보다 먼저 일어나므로 캡처에 없습니다. DNS 시간은 curl이 잰 값을 씁니다.

4준비: 노트북이 주소를 받습니다

이 단계는 명령을 실행하기 전에 끝납니다. 노트북이 Wi-Fi에 연결할 때 일어납니다. 5주차 3.9

  1. 노트북이 DHCP Request 메시지를 브로드캐스트합니다. 출발지 주소는 0.0.0.0입니다. 노트북에 아직 주소가 없기 때문입니다. 목적지 주소는 255.255.255.255입니다. 노트북은 이전에 받은 주소를 다시 쓰겠다고 묻습니다. → dhcp.pcapng #1
  2. DHCP 서버가 ACK로 답합니다. 서버는 172.16.0.7이고, 7.1 ms 뒤에 답했습니다. 노트북은 ACK의 값으로 다음 네 가지를 설정합니다.
    • 주소와 마스크: 172.16.25.130/24
    • 기본 게이트웨이: 172.16.25.1
    • DNS 서버의 주소
    • 임대 시간. 측정 시점에 1,293초가 남아 있었습니다.
    → dhcp.pcapng #2, addresses.json
처음 연결할 때

기억한 주소가 없으면 메시지가 4개입니다: Discover → Offer → Request → ACK. 핫스팟 캡처(dhcp.pcapng #3–#6)가 이 경우입니다. 4개 메시지는 34 ms 안에 끝났습니다.

5노트북이 이름을 주소로 바꿉니다

노트북은 이름으로 패킷을 보낼 수 없습니다. 먼저 주소를 얻어야 합니다. 3주차 1.4

  1. 사용자가 명령을 실행합니다. curl이 URL을 세 부분으로 나눕니다.
    부분값쓰는 곳
    스킴https포트 443과 TLS를 정합니다.
    이름speed.cloudflare.comDNS 질의에 씁니다.
    경로/__down?bytes=5000000HTTP 요청에 씁니다.
  2. curl이 운영체제에 주소를 묻습니다. 운영체제는 질의를 127.0.0.53으로 보냅니다. 이 주소는 노트북 안의 스텁 리졸버(systemd-resolved)입니다.
  3. 스텁 리졸버가 캐시를 확인합니다. 캐시에 답이 있으면 바로 답합니다. 답이 없으면 DHCP로 받은 DNS 서버에 재귀 질의를 보냅니다.
  4. 답이 옵니다: 172.66.0.218. 이름 해석은 1.7 ms 걸렸습니다. → time_namelookup
이 프로젝트에서 · 1.7 ms가 뜻하는 것

루트부터 반복 질의를 하면 훨씬 오래 걸립니다. 3주차 캡처에서 www.korea.ac.kr의 반복 질의는 365 ms 걸렸습니다.

패킷질의 대상응답걸린 시간
#1–#2루트 198.41.0.4위임: .kr 서버 목록과 glue288.7 ms
#3–#4.kr 서버 210.101.61.1위임: korea.ac.kr 서버와 glue5.3 ms
#5–#6권한 서버 163.152.11.6답: 163.152.6.1029.7 ms

그러므로 1.7 ms의 답은 캐시에서 왔습니다. 그 캐시는 노트북 안에 있거나 캠퍼스 DNS 서버에 있습니다. 이 측정으로는 둘을 구별할 수 없습니다.

핫스팟 측정에서는 캐시의 효과가 직접 보입니다. 첫 실행은 44.7 ms, 둘째 실행부터는 1.7–2.2 ms였습니다. → throughput.json

6노트북이 첫 홉을 정합니다

노트북은 서버로 가는 전체 경로를 모릅니다. 노트북은 첫 홉만 정합니다. 5주차 3.7

  1. 커널이 라우팅 표에서 목적지 172.66.0.218을 찾습니다. 커널은 최장 프리픽스 일치를 씁니다.
    항목다음 홉172.66.0.218과 일치?
    172.16.25.0/24직접 (같은 서브넷)아니오. 앞 24비트가 172.66.0입니다.
    172.17.0.0/16docker0아니오. 앞 16비트가 172.66입니다.
    0.0.0.0/0172.16.25.1예. 길이 0은 모든 주소와 일치합니다.
    일치한 항목은 기본 경로 하나입니다. 그러므로 첫 홉은 게이트웨이 172.16.25.1입니다. → addresses.json의 ip_route
  2. 노트북이 게이트웨이의 MAC 주소를 찾습니다. 노트북은 ARP를 씁니다. 7주차 5.5 이 단계 뒤에 프레임의 두 주소는 서로 다른 장치를 가리킵니다.
    • 프레임의 목적지 MAC 주소: 게이트웨이
    • IP 데이터그램의 목적지 주소: 서버 172.66.0.218

7노트북과 서버가 연결을 만듭니다

HTTPS는 TCP를 씁니다. 데이터를 보내기 전에 3-way handshake를 합니다. 4주차 2.7

  1. 운영체제가 소켓에 임시 포트를 붙입니다. 포트는 54826입니다. 연결은 다음 4개 값으로 구별합니다: (172.16.25.130, 54826, 172.66.0.218, 443). 4주차 2.2
  2. t = 0: 노트북이 SYN을 보냅니다. SYN에는 다음 값이 있습니다.
    • ISN: 1111356914
    • MSS 1460, 윈도우 스케일 10(×1024), SACK 허용
    • 윈도우 64,240. SYN의 윈도우에는 스케일을 적용하지 않습니다.
    • IP 헤더의 TTL: 64
    → #1
  3. 캠퍼스 NAT가 출발지를 바꿉니다. 출발지 172.16.25.130:54826을 163.152.233.xxx:새 포트로 바꿉니다. NAT는 이 대응을 변환 표에 기록합니다. 캡처는 노트북에서 했습니다. 그러므로 바뀐 값은 캡처에 없습니다. 5주차 3.10 → tracepath-campus.txt: 1·2번 홉은 사설 주소, 3번 홉 163.152.233.129부터 공인 주소
  4. 라우터들이 SYN을 서버까지 옮깁니다. 각 라우터는 목적지 주소로 출력 링크를 고릅니다. 각 라우터는 TTL을 1 줄입니다. 노트북에 도착한 서버 패킷의 TTL은 55였습니다. 서버가 64로 보냈다면 라우터 9개를 지났습니다.
  5. t = 8.7 ms: 서버가 SYN+ACK를 보냅니다.
    • 서버의 ISN: 3798358670
    • ack: 1111356915 = 노트북의 ISN + 1. SYN이 순서 번호 하나를 씁니다.
    • MSS 1250, 윈도우 스케일 13(×8192)
    NAT는 변환 표를 찾습니다. NAT는 목적지를 172.16.25.130:54826으로 되돌립니다. 8.7 ms가 이 연결의 첫 RTT 표본입니다. → #2
  6. t = 8.8 ms: 노트북이 ACK를 보냅니다. 연결이 만들어졌습니다. 노트북은 서버에 1250바이트 이하의 세그먼트를 보냅니다. 서버는 노트북에 1460바이트 이하의 세그먼트를 보냅니다. → #3

8노트북이 암호화를 맞추고 요청을 보냅니다

HTTPS는 TCP 위에서 TLS로 암호화합니다. TLS는 이 강의의 범위 밖입니다. 이 페이지는 순서만 씁니다.

  1. t = 13.8 ms: 노트북이 TLS ClientHello를 보냅니다. 노트북이 쓸 수 있는 암호 방식을 알립니다. → #4
  2. t = 20.0 ms: 서버가 TLS 응답을 보냅니다. ClientHello부터 6.2 ms 걸렸습니다. 왕복 한 번입니다. → #6
  3. t = 25.1 ms: 노트북이 TLS 협상을 끝냅니다. → #8
  4. t = 25.6 ms: 노트북이 HTTP 요청을 보냅니다. 요청의 내용은 GET /__down?bytes=5000000입니다. 요청은 암호화되어 있습니다. 그러므로 캡처에서 이 내용을 읽을 수 없습니다. → #9

9서버가 데이터를 보냅니다

서버는 5 MB를 보냅니다. 보내는 양은 혼잡 윈도우와 수신 윈도우로 정해집니다. 4주차 2.12

  1. t = 56.4 ms: 첫 응답 데이터가 도착합니다. 요청을 보내고 30.8 ms 뒤입니다. RTT는 약 8.7 ms입니다. 그러므로 남은 약 22 ms는 네트워크가 아닌 서버 쪽에서 쓴 시간으로 보입니다. → #11
  2. 서버가 슬로 스타트로 보냅니다. 첫 묶음 #11–#18은 0.2 ms 안에 도착합니다. 노트북은 ACK(#19)로 답합니다. ACK가 올 때마다 서버의 혼잡 윈도우가 커집니다. 그러므로 묶음은 RTT마다 커집니다.
  3. 노트북의 수신 윈도우가 커집니다. 36,864바이트(#19)에서 4,588,544바이트(#282)까지 커졌습니다. 그러나 전송 중인 데이터는 최대 약 193 KB였습니다. 그러므로 제한한 것은 수신 윈도우가 아닌 혼잡 윈도우입니다. 이 값은 BDP(179 Mbps × 7.5 ms ≈ 168 KB)와 같은 크기입니다. 4주차 2.10
  4. 서버가 마지막 데이터를 보냅니다. 서버는 5,014,135바이트를 보냈습니다. 본문 5,000,000바이트에 HTTP 헤더와 TLS의 추가 바이트가 더해진 값입니다.
캡처에 MSS보다 큰 패킷이 보이는 이유

캡처에는 64,376바이트의 패킷도 있습니다. 이 값은 MSS 1460보다 큽니다. 네트워크 카드와 커널이 받은 세그먼트를 합친 뒤에 캡처 프로그램이 봤기 때문입니다(GRO). 보내는 쪽도 같습니다(TSO). 1,646바이트의 ClientHello(#4)가 그 예입니다. 링크 위의 실제 세그먼트는 MSS 이하입니다.

10노트북과 서버가 연결을 닫습니다

  1. t = 145.9 ms: 노트북이 FIN을 보냅니다. 노트북은 더 보낼 데이터가 없습니다. → #282
  2. t = 149.8 ms: 서버도 FIN을 보냅니다. 이 FIN의 ack는 1811입니다. 이 값은 노트북의 FIN을 아직 확인하지 않은 값입니다. 두 FIN이 거의 같은 때에 엇갈렸습니다. → #283
  3. t = 153.3 ms: 양쪽이 상대의 FIN을 ACK로 확인합니다. 연결이 닫혔습니다. 캡처에는 모두 285개 패킷이 있습니다. NAT의 변환 표 항목은 일정 시간 뒤에 지워집니다. → #284, #285

11직접 확인하기

시작하기 전에
  • VPN과 터널(Cloudflare WARP, Tailscale 등)이 켜져 있는지 확인하십시오. 켜져 있으면 경로와 시간이 바뀝니다.
  • 원본 캡처는 raw/에 두십시오. out/에 넣기 전에 mask.py로 마스킹하십시오.
절차
  1. 첫 홉을 확인하십시오. 
    ip route get 172.66.0.218
    결과의 via 뒤에 기본 게이트웨이의 주소가 있어야 합니다.
  2. DNS 캐시를 확인하십시오. 같은 명령을 두 번 실행하십시오. 
    resolvectl query speed.cloudflare.com
    두 번째 결과에 Data from: cache가 있어야 합니다.
  3. 다른 터미널에서 캡처를 시작하십시오. <인터페이스>에는 Wi-Fi 인터페이스의 이름을 쓰십시오. 
    sudo tcpdump -i <인터페이스> -w raw/req.pcap tcp port 443
  4. 요청을 보내고 구간별 시간을 출력하십시오. 
    curl -o /dev/null -s -w 'dns %{time_namelookup}  tcp %{time_connect}  tls %{time_appconnect}  first %{time_starttransfer}  total %{time_total}\n' \
  https://speed.cloudflare.com/__down?bytes=5000000
  5. 캡처를 멈추십시오 (Ctrl+C).
  6. 처음 3개 패킷을 확인하십시오. 
    tshark -r raw/req.pcap -c 3
    SYN, SYN+ACK, ACK가 차례로 있어야 합니다.
  7. 4단계의 시간과 캡처의 시각을 이 페이지의 시간표와 비교하십시오.

✓스스로 확인하기

확인 질문
노트북이 보낸 프레임에서 목적지 MAC 주소와 목적지 IP 주소는 왜 다른 장치를 가리킵니까?
IP 주소는 마지막 목적지(서버)를 가리킵니다. MAC 주소는 이 링크의 다음 장치(게이트웨이)를 가리킵니다. 라우터를 지날 때마다 프레임은 새로 만들어지고, IP 목적지 주소는 그대로 남습니다.
핫스팟의 첫 실행에서 DNS는 44.7 ms, 둘째 실행에서는 1.8 ms였습니다. 왜 다릅니까?
첫 실행의 답은 캐시에 없었습니다. 그래서 리졸버가 다른 서버에 질의했습니다. 둘째 실행부터는 TTL이 지나지 않은 답이 캐시에 있었습니다.
SYN+ACK의 ack가 1111356915인 이유는 무엇입니까?
노트북의 ISN은 1111356914입니다. SYN은 데이터가 없지만 순서 번호 하나를 씁니다. 그러므로 서버가 다음에 기다리는 번호는 ISN + 1입니다.
수신 윈도우는 4.6 MB까지 열렸습니다. 그러나 전송 중인 데이터는 약 193 KB였습니다. 무엇이 양을 제한했습니까?
서버의 혼잡 윈도우입니다. 보내는 양은 min(수신 윈도우, 혼잡 윈도우)입니다. 전송이 약 17 RTT 만에 끝났으므로, 혼잡 윈도우는 대부분 슬로 스타트 중이었습니다.
NAT가 주소를 바꾸는 모습이 이 캡처에 보이지 않는 이유는 무엇입니까?
캡처는 노트북에서 했습니다. 노트북은 NAT 안쪽에 있습니다. 노트북에서는 바뀌기 전의 주소(172.16.25.130)만 보입니다. 바뀐 주소는 NAT 바깥에서 캡처해야 보입니다.
