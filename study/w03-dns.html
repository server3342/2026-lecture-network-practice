1.9

1.1DNS가 해결하는 문제

개념

호스트를 가리키는 방법은 두 가지입니다.

이름 www.korea.ac.kr

사람이 기억하기 쉽습니다. 길이가 일정하지 않습니다. 라우터는 이름을 처리하지 않습니다.

주소 163.152.6.10

32비트 숫자입니다. 라우터가 처리합니다. 사람이 기억하기 어렵습니다.

DNS(Domain Name System)는 이름을 주소로 바꿉니다. 이 일을 이름 해석(name resolution)이라고 합니다.

주소 변환 이외의 서비스

서비스설명
호스트 별칭짧은 별칭을 정식 이름(canonical name)에 연결합니다.
메일 서버 별칭@korea.ac.kr 메일을 받을 서버를 알려 줍니다(MX).
부하 분산한 이름에 여러 주소를 돌려줍니다. 클라이언트가 여러 서버로 나뉩니다.

DNS는 응용 계층 프로토콜입니다. 주로 UDP 53번 포트를 사용합니다. 응답이 크면 TCP 53번을 사용합니다.

1.2왜 DNS를 한 대의 서버로 만들지 않는가

중앙 서버 한 대로 만들면 네 가지 문제가 생깁니다.

① 단일 장애점

그 서버가 멈추면 인터넷 전체가 멈춥니다.

② 트래픽 양

전 세계의 모든 질의가 한 서버로 갑니다.

③ 거리

먼 사용자는 질의마다 긴 지연을 겪습니다.

④ 유지보수

모든 이름의 변경을 한 곳에서 처리해야 합니다.

결론

DNS는 분산(distributed)되고 계층적(hierarchical)인 데이터베이스입니다.

영역(zone)은 한 조직이 책임지는 이름의 범위입니다.

1.4재귀 질의와 반복 질의

재귀 질의 (recursive)

"답을 끝까지 찾아서 주십시오."

받은 서버가 다른 서버들에게 대신 묻습니다.

반복 질의 (iterative)

"아는 만큼만 주십시오."

받은 서버는 다음에 물을 서버를 알려 줍니다.

절차 · 보통의 이름 해석
  1. 노트북이 로컬 DNS 서버에 재귀 질의를 보냅니다.
  2. 로컬 DNS 서버가 루트 서버에 반복 질의를 보냅니다. 루트 서버는 TLD 서버의 위치를 줍니다.
  3. 로컬 DNS 서버가 TLD 서버에 질의합니다. TLD 서버는 권한 서버의 위치를 줍니다.
  4. 로컬 DNS 서버가 권한 서버에 질의합니다. 권한 서버는 주소를 줍니다.
  5. 로컬 DNS 서버가 주소를 노트북에 돌려줍니다. 결과를 캐시에 저장합니다.

노트북은 질의를 한 번 보냅니다. 나머지 질의는 로컬 DNS 서버가 보냅니다.

RD 비트

질의 헤더의 RD(Recursion Desired) 비트가 1이면 "재귀로 처리해 주십시오"라는 뜻입니다. dig의 +norecurse 옵션은 RD를 0으로 만듭니다.

이 프로젝트에서 · Task 1

Task 1은 위 그림의 ②–⑦을 직접 구현하는 과제입니다. dig +trace는 이 일을 대신 하므로 금지입니다. _query()는 모든 질의에 +norecurse를 붙입니다(81–84행).

1.7위임(delegation)과 glue 레코드

개념

위임은 "이 이름은 내 담당이 아닙니다. 저 서버에 물으십시오"라는 응답입니다. Authority 섹션의 NS 레코드로 표현됩니다.

NS의 값은 서버의 이름입니다. 이름만으로는 질의를 보낼 수 없습니다. 주소가 필요합니다.

그래서 위임 응답은 보통 Additional 섹션에 그 서버들의 A 레코드를 함께 넣습니다. 이것이 glue 레코드입니다.

glue가 있을 때

위임 받음→glue 주소로
바로 질의

추가 비용 없음

glue가 없을 때

위임 받음→원래 해석 멈춤→NS 이름을
루트부터 해석→원래 해석 계속

해석 안의 해석 = "재귀 리졸버"의 "재귀"

_walk() 128–145행이 위임을 처리합니다.

    servers.append(self.resolve_inner(n, depth + 1))              # NS 이름부터 새로 해석

1.9DNS 캐시와 TTL

개념

DNS 서버는 받은 레코드를 캐시에 저장합니다. 같은 질의가 다시 오면 캐시에서 답합니다. 그래서 실제로 루트까지 가는 질의는 적습니다.

캐시는 레코드를 TTL 동안만 사용해야 합니다.

  • 시각 t에 TTL이 T초인 레코드를 받았습니다.
  • 이 레코드는 [t, t+T) 구간의 질의에만 답할 수 있습니다.
  • t+T 이후에 이 레코드로 답하면 만료된 답(stale answer)입니다.
이 프로젝트에서 · Task 3

BaselineCache는 결함이 세 개입니다. 앞의 두 개는 원인이 같습니다: TTL을 버리고 모든 레코드를 60초 동안 유지합니다(FIXED_LIFETIME = 60).

결함종류결과
TTL이 60초보다 짧은 레코드를 만료 후에도 줌정확성stale 266건 (microsoft 20초, cnn 30초)
TTL이 긴 레코드를 1분마다 다시 가져옴성능dns.google을 1번이면 될 것을 21번
리스트를 처음부터 끝까지 찾음성능조회마다 O(n)

YourCache는 레코드마다 만료 시각을 저장합니다.

entry = self.entries.get(name)                     # dict: O(1) 조회
if entry is not None and now < entry[1]:           # 만료 전 → 캐시에서 답
    return entry[0]
address, ttl = self.upstream(name)                 # 없거나 만료 → 상류에 질의
self.entries[name] = (address, now + ttl)          # 만료 시각 = 지금 + TTL

266

stale · 상류 325 · hit 67.5%

YourCache

0

stale · 상류 275 · hit 72.5%

하한 275의 이유
  1. 레코드는 받은 뒤 TTL 동안만 사용할 수 있습니다.
  2. 만료 후 첫 질의는 반드시 상류에 물어야 합니다. 그렇지 않으면 stale입니다.
  3. 더 일찍 다시 물으면 질의 수만 늘어납니다.
  4. 따라서 "만료 후 첫 질의에서만 다시 묻기"가 최소입니다. YourCache가 정확히 이 방법입니다.

자료구조를 바꿔도 이 수는 줄지 않습니다. TTL과 질의 패턴이 하한을 정합니다. (microsoft 118 + cnn 76 + netflix 37 + spotify 23 + github 11 + wikipedia 6 + 긴 TTL 4개 × 1 = 275)

1.10비디오 스트리밍과 DASH

개념

비디오는 큰 데이터를 끊김 없이 받아야 합니다. 사용자마다 대역폭이 다르고, 대역폭은 시간에 따라 변합니다. DASH(Dynamic Adaptive Streaming over HTTP)는 이 문제를 클라이언트가 풀게 합니다.

  1. 서버는 비디오를 짧은 조각(chunk)으로 나눕니다.
  2. 서버는 각 조각을 여러 비트율로 인코딩합니다.
  3. 서버는 매니페스트(manifest) 파일에 조각과 비트율별 URL을 적습니다.
  4. 클라이언트는 매니페스트를 먼저 받습니다.
  5. 클라이언트는 측정한 대역폭과 버퍼 양을 보고 다음 조각의 비트율을 고릅니다.

누가 고르는가

서버가 아니라 클라이언트가 비트율을 고릅니다.

왜 HTTP인가

일반 웹 서버, 캐시, 방화벽을 그대로 통과합니다.

버퍼의 역할

재생 전에 미리 받아 둔 데이터가 속도 변동을 흡수합니다.

1.11CDN과 DNS 유도

개념

데이터센터 한 곳에서 전 세계에 보내면 ① 먼 경로의 가장 느린 링크가 속도를 정하고 ② 같은 데이터가 같은 링크를 여러 번 지나며 ③ 데이터센터가 단일 장애점이 됩니다.

CDN(Content Distribution Network)은 많은 위치에 서버 클러스터를 두고 콘텐츠 복사본을 저장합니다.

Enter Deep

ISP 안 깊이, 많은 곳에 작은 클러스터. 사용자와 가깝습니다. 관리가 어렵습니다. (예: Akamai)

Bring Home

IXP 근처, 적은 곳에 큰 클러스터. 관리가 쉽습니다. 사용자와 덜 가깝습니다.

DNS가 사용자를 클러스터로 보내는 방법

주의

④에서 CDN이 보는 것은 사용자가 아니라 로컬 DNS 서버의 주소입니다. 사용자가 먼 공용 리졸버(예: 8.8.8.8)를 쓰면 CDN은 사용자의 위치를 잘못 알 수 있습니다.

애니캐스트 (anycast)

여러 위치의 서버가 같은 주소를 씁니다. 라우팅이 가까운 위치로 보냅니다. CNAME이 없으므로 DNS만 보아서는 CDN을 알 수 없습니다. 6주차에 traceroute로 1.1.1.1까지 가 보면 13홉, 12 ms 만에 국내의 복제 서버가 답합니다(6주차 4.9).

AS (Autonomous System)

한 조직이 운영하는 네트워크입니다. 번호(ASN)를 가집니다. 주소의 AS를 보면 그 주소의 실제 소유자를 알 수 있습니다.

1.12(참고) 전자메일

3주차 강의 앞부분입니다. 실습에서는 사용하지 않았습니다.

사용자 에이전트SMTP → Alice의
메일 서버SMTP → Bob의

사용자 에이전트
  • SMTP는 서버에서 서버로 메일을 밀어 보냅니다(push). TCP 25번 포트입니다.
  • HTTP는 클라이언트가 데이터를 당겨 옵니다(pull).
  • 받은 메일을 가져오는 일은 SMTP가 하지 않습니다. IMAP 또는 HTTP(웹메일)가 합니다.
  • DNS의 MX 레코드가 도메인의 메일 서버를 알려 줍니다.

루트 서버는 왜 www.korea.ac.kr의 주소를 바로 주지 않습니까?

루트 서버는 그 주소를 가지고 있지 않습니다. 루트 서버는 kr을 누가 담당하는지만 압니다. 그래서 위임만 줄 수 있습니다.

노트북은 질의를 1번 보냅니다. Task 1 리졸버는 3번 이상 보냈습니다. 차이는 누가 합니까?

로컬 DNS 서버(리졸버)가 합니다. 노트북의 재귀 질의를 받아 반복 질의로 계층을 내려가고, 결과를 캐시합니다.

위임 응답과 답 응답을 패킷에서 어떻게 구별합니까?

위임: Answer 0개, Authority에 NS, AA=0. 답: Answer에 A, AA=1. 형식은 같고 채워진 섹션만 다릅니다.

glue가 없는 위임을 받으면 리졸버는 무엇을 합니까?

원래 해석을 멈추고 NS 이름의 주소를 루트부터 새로 해석합니다. 그 주소로 원래 해석을 이어 갑니다.

상류 질의 하한이 275인 이유는 무엇입니까?

레코드는 TTL 동안만 쓸 수 있습니다. 만료 후 첫 질의는 반드시 상류에 물어야 합니다. 더 일찍 물으면 질의만 늘어납니다. 그래서 "만료 후 첫 질의에서만 묻기"의 횟수가 최소입니다.

www.microsoft.com의 상류 질의가 baseline 52건에서 118건으로 늘었습니다. 왜 이것이 옳습니까?

baseline이 아낀 질의는 만료된 답이었습니다. TTL이 20초이므로 올바른 캐시는 그 질의를 해야 합니다.

리졸버를 바꾸면 다른 주소가 온다는 사실로 "가까운 곳으로 보낸다"를 증명할 수 없는 이유는?

같은 리졸버에 두 번 물어도 주소가 바뀝니다(순환). 그리고 지연을 재지 않았으므로 다른 주소가 더 가까운지 모릅니다.
