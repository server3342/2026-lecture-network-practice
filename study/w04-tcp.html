2.1전송 계층의 자리

네트워크 계층 (IP)

호스트와 호스트를 연결합니다.

전송 계층 (TCP, UDP)

프로세스와 프로세스를 연결합니다.

IP는 최선형(best-effort) 서비스입니다

IP는 다음을 보장하지 않습니다.

  • 패킷이 도착하는 것
  • 보낸 순서대로 도착하는 것
  • 한 번만 도착하는 것
  • 손상 없이 도착하는 것

TCP는 이 위에서 신뢰적 전송을 만듭니다. UDP는 거의 아무것도 더하지 않습니다.

2.2포트 번호와 다중화

개념

한 호스트에서 여러 프로세스가 동시에 통신합니다. 전송 계층은 포트 번호(16비트, 0–65535)로 프로세스를 구분합니다.

  • 다중화(multiplexing): 송신 측에서 여러 소켓의 데이터에 헤더를 붙여 내려보냅니다.
  • 역다중화(demultiplexing): 수신 측에서 헤더를 보고 맞는 소켓에 넘깁니다.
프로토콜소켓을 구분하는 값결과
UDP(목적지 IP, 목적지 포트) — 2개출발지가 달라도 같은 소켓으로 갑니다.
TCP(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트) — 4개443번 포트 하나로 연결마다 다른 소켓을 씁니다.

연결 설정 없음

상태 없음

8바이트. TCP는 20바이트 이상입니다.

속도를 응용이 정함

혼잡 제어가 보내는 속도를 줄이지 않습니다.

체크섬

송신 측은 세그먼트를 16비트 단위로 더하고 1의 보수를 취해 넣습니다. 수신 측은 같은 계산을 합니다. 결과가 맞지 않으면 오류가 있습니다. 체크섬은 오류를 발견합니다. 오류를 고치지 않습니다.

2.4신뢰적 데이터 전송의 문제

신뢰할 수 없는 채널은 패킷에 네 가지 일을 합니다. 각 문제에는 해결 장치가 있습니다.

손상 (corruption)

→ 체크섬

손실 (loss)

→ ACK + 타이머 + 재전송

중복 (duplication)

→ 순서 번호

순서 바뀜 (reordering)

→ 순서 번호 + 수신 버퍼

장치역할
순서 번호각 패킷에 번호를 붙입니다. 수신 측은 번호로 중복과 순서를 판단합니다.
ACK수신 측이 "이 번호를 받았습니다"라고 알립니다.
타이머송신 측이 ACK를 일정 시간 기다립니다.
재전송타이머가 끝날 때까지 ACK가 없으면 다시 보냅니다.
핵심: 재전송은 중복을 만듭니다
  1. 수신 측이 데이터를 받고 ACK를 보냅니다.
  2. 그 ACK가 손실됩니다.
  3. 송신 측은 데이터가 손실되었다고 판단하고 다시 보냅니다.
  4. 수신 측은 같은 데이터를 두 번 받습니다. 순서 번호가 없으면 이것을 구별할 수 없습니다.

순서 번호는 바이트 단위
seq 50001,000바이트→ seq 60001,000바이트→ ACK 7000"6999까지 모두 받음, 다음은 7000"

ISN은 왜 0이 아닌가

첫 순서 번호(ISN, Initial Sequence Number)는 각 쪽이 예측하기 어려운 값으로 고릅니다.

  1. 공격자가 순서 번호를 추측해서 가짜 세그먼트를 넣는 것을 막습니다.
  2. 같은 4개 값으로 만든 이전 연결의 늦은 세그먼트가 새 연결의 데이터로 섞이는 것을 막습니다.

Task 1과의 비교: Task 1은 패킷 번호(0, 1, 2, …)를 씁니다. TCP는 바이트 번호를 씁니다. 원리는 같습니다.

2.8RTT 추정과 타임아웃

타임아웃이 너무 짧으면

불필요한 재전송이 생깁니다.

타임아웃이 너무 길면

손실에 늦게 반응합니다.

EstimatedRTT    = (1 − α)·EstimatedRTT + α·SampleRTT                 # α = 0.125
DevRTT          = (1 − β)·DevRTT + β·|SampleRTT − EstimatedRTT|      # β = 0.25
TimeoutInterval = EstimatedRTT + 4·DevRTT
빠른 재전송 (fast retransmit)

같은 ACK가 세 번 더 오면(중복 ACK 3개) 타이머를 기다리지 않고 재전송합니다. 중복 ACK는 "그 뒤의 세그먼트는 도착하고 있다"는 뜻입니다. 한 세그먼트만 빠졌을 가능성이 큽니다.

이 프로젝트의 타임아웃은 고정 값입니다: Task 1 TIMEOUT = 40, Task 3 bench TIMEOUT = 3 * RTT. 시뮬레이션이라 RTT 추정이 필요 없습니다.

2.9흐름 제어

개념

흐름 제어(flow control)는 송신 측이 수신 측의 버퍼를 넘치게 하지 않도록 합니다.

  1. 수신 측은 버퍼의 남은 공간을 rwnd 필드에 넣어 보냅니다.
  2. 송신 측은 확인되지 않은 데이터의 양을 rwnd 이하로 유지합니다.

실제 윈도우 = 필드 값 × 2스케일. SYN 자체의 윈도우 필드에는 스케일을 적용하지 않습니다.

2.11혼잡과 혼잡 제어

개념

혼잡(congestion)은 너무 많은 송신자가 네트워크의 처리량보다 많이 보낼 때 생깁니다.

① 큐 지연

도착률이 링크 용량에 가까워지면 지연이 매우 커집니다.

② 재전송 낭비

버린 패킷을 다시 보내므로 같은 데이터에 링크를 두 번 씁니다.

③ 상류의 낭비

중간에서 버려진 패킷은 앞 링크들이 한 일을 버립니다.

1986년 10월 · 혼잡 붕괴

링크는 바빴지만 대부분 재전송이었습니다. 유효 처리량은 거의 0이었습니다. TCP 혼잡 제어는 이 사건 뒤에 만들어졌습니다.

2.12TCP 혼잡 제어: 슬로 스타트와 AIMD

개념

송신 측은 라우터의 큐를 볼 수 없습니다. 두 가지 사건으로 추정합니다.

ACK 도착

여유가 있습니다 → cwnd를 늘립니다.

손실

큐가 넘쳤습니다 → cwnd를 줄입니다.

단계규칙결과
슬로 스타트cwnd = 1 MSS로 시작. ACK마다 +1 MSS. ssthresh에 닿으면 혼잡 회피로.RTT마다 두 배 (지수 증가)
혼잡 회피ACK마다 +MSS·MSS/cwndRTT마다 +1 MSS (선형 증가)
중복 ACK 3개ssthresh = cwnd/2, cwnd 절반 → 빠른 회복 (Reno)가벼운 신호
타임아웃ssthresh = cwnd/2, cwnd = 1 MSS → 슬로 스타트심한 신호

혼잡 회피의 "선형 증가 + 절반 감소"가 AIMD(Additive Increase, Multiplicative Decrease)입니다. cwnd는 톱니 모양으로 움직입니다.

def on_ack(self):
    if self.slow_start:
        self.window += 1                          # 슬로 스타트: RTT마다 두 배
    else:
        self.window += self.GROW / self.window    # 혼잡 회피: RTT마다 +0.25

def on_loss(self):
    if self.quiet > 0:
        return                                    # 한 번의 넘침 = 한 번의 감소
    self.slow_start = False
    self.window = max(2.0, self.window * self.BACKOFF)   # ×0.5
    self.quiet = int(self.window) * self.QUIET

지연 기반 혼잡 제어

손실 기반 방식은 큐가 넘쳐야 반응합니다. 그래서 큐를 늘 채웁니다. 지연 기반 방식(TCP Vegas, BBR)은 RTT가 늘어나는 것을 보고 큐가 차기 전에 줄입니다.

2.13QUIC

개념

QUIC은 UDP 위에서 동작하는 전송 프로토콜입니다. HTTP/3이 사용합니다.

왜 UDP 위인가: 운영체제와 중간 장비(방화벽, NAT)는 TCP를 이미 해석합니다. TCP를 바꾸면 그 장비들이 새 TCP를 막거나 고칩니다. UDP 위에서는 응용 안에서 새 기능을 배포할 수 있습니다.

  • 연결 설정과 TLS 암호화 설정을 한 번의 왕복으로 합칩니다.
  • 한 연결 안에 여러 스트림을 둡니다. 한 스트림의 손실이 다른 스트림을 막지 않습니다.
  • TCP처럼 신뢰적 전송과 혼잡 제어를 합니다.

TCP 소켓은 왜 값 4개로 구분하고, UDP는 2개로 충분합니까?

TCP는 연결마다 상태(순서 번호, 버퍼)가 따로 있습니다. 같은 서버 포트에 들어온 연결을 구분하려면 출발지 주소와 포트가 필요합니다. UDP는 연결 상태가 없습니다.

수신 측이 중복 데이터 패킷에도 ACK를 다시 보내야 하는 이유는?

처음 ACK가 손실되었을 수 있습니다. 다시 보내지 않으면 송신 측은 그 패킷을 끝없이 재전송합니다.

SYN-ACK의 ack 번호가 클라이언트 ISN + 1인 이유는?

SYN은 데이터가 없어도 순서 번호 1개를 사용합니다. ack는 "다음에 기대하는 번호"이므로 ISN + 1입니다.

rwnd가 4.6 MB였는데 실제로 보낸 양은 193 KB였습니다. 무엇이 제한했습니까?

송신 측의 혼잡 윈도우(cwnd)입니다. 5 MB 전송이 0.15초에 끝나서 대부분 슬로 스타트 중이었습니다. 193 KB는 BDP(약 168 KB)와 같은 크기입니다.

흐름 제어와 혼잡 제어의 차이를 한 문장으로 말하십시오.

흐름 제어는 수신 측 버퍼를 보호하고 rwnd로 직접 알림을 받습니다. 혼잡 제어는 네트워크를 보호하고 손실과 지연으로 상태를 추정합니다.

고정 윈도우 64가 goodput이 가장 높은데도 가장 나쁜 송신자인 이유는?

37%를 버리고 큐를 늘 가득 채워서 다른 흐름에 지연과 손실을 줍니다. goodput은 그 피해를 세지 않습니다. 모두가 이렇게 하면 혼잡 붕괴입니다.

타임아웃과 중복 ACK 3개에 TCP가 다르게 반응하는 이유는?

중복 ACK는 뒤의 세그먼트가 도착하고 있다는 뜻이므로 가벼운 혼잡입니다(절반). 타임아웃은 아무것도 도착하지 않는다는 뜻이므로 심한 혼잡입니다(1 MSS로).
