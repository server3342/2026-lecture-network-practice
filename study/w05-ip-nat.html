포워딩 (forwarding)

라우터 하나가 들어온 패킷을 알맞은 출력 링크로 보냅니다.

나노초 단위 · 데이터 평면 · 5주차

라우팅 (routing)

출발지에서 목적지까지의 경로 전체를 정합니다.

초 단위 · 제어 평면 · 6주차

포워딩은 포워딩 테이블을 사용합니다. 라우팅이 이 테이블을 만듭니다.

3.2라우터 내부

입력 큐 HOL 블로킹

맨 앞 패킷이 막히면, 뒤의 패킷은 출력 포트가 비어 있어도 기다립니다.

출력 포트 큐잉

여러 입력이 한 출력으로 몰리면 큐가 찹니다. 가득 차면 버립니다(tail drop).

다음에 보낼 패킷을 고릅니다: FIFO, 우선순위, 라운드 로빈, WFQ.

이름만 같은 두 TTL

IP 헤더의 TTL

홉 수입니다. 라우터마다 1씩 줄고 0이 되면 버립니다. 무한 순환을 막습니다.

DNS 레코드의 TTL

초입니다. 캐시에 둘 수 있는 시간입니다. (3주차 1.9)

이 프로젝트에서 · tracepath

Task 2의 tracepath는 IP TTL을 1, 2, 3, …으로 늘려 보냅니다. TTL이 0이 된 라우터가 오류 메시지를 돌려보냅니다. 그래서 경로의 각 라우터 주소를 알 수 있습니다.

단편화: 링크마다 최대 전송 단위(MTU)가 다릅니다. 큰 데이터그램은 조각으로 나뉘고, 목적지 호스트에서만 다시 합칩니다. IPv6는 라우터에서 단편화하지 않습니다.

3.4IPv4 주소와 32비트 정수

개념

IPv4 주소는 32비트 정수입니다. 사람이 읽기 위해 8비트씩 네 부분으로 나누어 10진수로 씁니다(dotted-decimal).

주소는 호스트가 아니라 인터페이스에 붙습니다. 라우터는 인터페이스가 여러 개이므로 주소도 여러 개입니다.

옥텟163152610
자리 값× 224× 216× 28× 1
합163·16,777,216 + 152·65,536 + 6·256 + 10 = 2,744,649,226
이 프로젝트에서 · Task 1 _to_int

Task 1은 ipaddress와 socket.inet_aton을 금지합니다(R6). 시프트와 OR로 직접 계산합니다.

value = 0
for part in parts:                       # "163", "152", "6", "10"
    value = (value << 8) | int(part)     # 8비트 왼쪽으로 밀고 새 8비트를 붙임
  1. value = 0
  2. (0 << 8) | 163 = 163
  3. (163 << 8) | 152 = 41,880
  4. (41,880 << 8) | 6 = 10,721,286
  5. (10,721,286 << 8) | 10 = 2,744,649,226

_to_str는 반대로 합니다: (value >> 24) & 0xFF, (value >> 16) & 0xFF, … 로 8비트씩 꺼냅니다.

3.5서브넷, 마스크, CIDR

개념

서브넷(subnet)은 라우터를 거치지 않고 서로 직접 닿는 인터페이스들의 집합입니다. 같은 서브넷의 주소는 앞부분이 같습니다. 이 앞부분이 프리픽스(prefix)입니다.

CIDR 표기 a.b.c.d/x: 앞의 x비트가 네트워크 부분, 나머지 32−x비트가 호스트 부분입니다.

네트워크 부분 (프리픽스)호스트 부분
프리픽스마스크호스트 비트주소 수
/8255.0.0.02416,777,216
/16255.255.0.01665,536
/20255.255.240.0124,096
/24255.255.255.08256
/26255.255.255.192664
/30255.255.255.25224
절차 · 주소 범위 구하기
  1. 마스크를 만드십시오: mask = (0xFFFFFFFF << (32 − x)) & 0xFFFFFFFF
  2. 네트워크 주소를 구하십시오: net = addr & mask (호스트 비트를 모두 0으로)
  3. 브로드캐스트 주소를 구하십시오: bcast = net | ~mask (호스트 비트를 모두 1로)
  4. 사용 가능 범위: net + 1 ~ bcast − 1

계산 예시: 172.16.32.0/20

네트워크172.16.32.0 첫 사용 가능172.16.32.1~ 마지막 사용 가능172.16.47.254 브로드캐스트172.16.47.255

  • _mask(0)은 0이어야 합니다. 파이썬 정수는 커지므로 0xFFFFFFFF << 32를 & 0xFFFFFFFF로 32비트에 잘라야 합니다.
  • parse_cidr는 프리픽스 길이가 0–32 밖이면 거부합니다(R1).
  • parse_cidr는 호스트 비트가 켜진 값을 거부합니다(R2). 163.152.6.5/24는 네트워크가 아니라 호스트입니다.
if net & ~_mask(plen) & 0xFFFFFFFF:      # 호스트 비트 중 하나라도 1이면
    raise ValueError(...)

3.7경로 집약과 최장 프리픽스 일치

개념

포워딩 테이블은 주소마다가 아니라 프리픽스마다 항목을 둡니다.

경로 집약(route aggregation): ISP가 여러 고객 프리픽스를 짧은 프리픽스 하나로 묶어 광고합니다. 예: 200.23.16.0/23, 200.23.18.0/23, … → 200.23.16.0/20.

한 주소가 여러 항목에 일치할 수 있습니다. 라우터는 가장 긴 프리픽스를 고릅니다. 이것이 최장 프리픽스 일치(LPM)입니다.

왜 가장 긴 것인가

더 긴 프리픽스는 더 구체적인 경로입니다. 예외는 구체성으로 표현됩니다. 고객이 다른 ISP로 옮기면 새 ISP는 그 고객의 긴 프리픽스를 광고합니다. 그 긴 프리픽스가 옛 ISP의 짧은 집약 프리픽스를 이깁니다.

기본 경로 0.0.0.0/0은 길이가 0입니다. 모든 주소에 일치하므로, 다른 항목이 하나라도 일치하면 집니다.

계산 예시: 10.20.30.70은 어디로 가는가

절차 · LPM
  1. 테이블의 각 항목 (net, x)에 대해 addr & mask(x) == net인지 검사하십시오.
  2. 일치한 항목 중에서 x가 가장 큰 항목을 고르십시오.
  3. 그 항목의 다음 홉을 돌려주십시오. 일치가 없으면 경로가 없습니다.
이 프로젝트에서 · Task 1 R4–R5

ForwardingTable은 프리픽스 길이별 dict를 씁니다. 긴 길이부터 찾으므로 처음 일치한 항목이 답입니다.

for plen in sorted(self.by_len, reverse=True):     # 긴 길이부터
    hop = self.by_len[plen].get(addr & _mask(plen))  # 그 길이로 마스크한 값을 찾음
    if hop is not None:
        return hop                                   # 처음 찾은 것 = 가장 긴 것

같은 네트워크·같은 길이에 다른 다음 홉을 넣으면 add()가 ValueError를 냅니다. 테이블이 모호하면 일부 패킷이 아무도 의도하지 않은 곳으로 가기 때문입니다.

3.8빠른 최장 프리픽스 일치

왜 빨라야 하는가

인터넷 라우팅 테이블은 약 100만 항목입니다. 1 Gbps 링크는 초당 약 100만 개의 작은 패킷을 나릅니다. 조회는 패킷 하나당 1 µs 이내여야 합니다.

방법조회 작업량메모리
선형 탐색 (baseline)항목 수 N에 비례N에 비례
길이별 해시 (Task 1)최대 33번 해시 조회N에 비례
이진 트라이최대 32단계 (주소 비트 수)N에 비례
직접 인덱스 DIR-24-8 (Task 3)배열 읽기 1번고정 224칸 = 64 MB

이 프로젝트에서 · Task 3
  1. 224칸 배열을 만듭니다. 칸 하나 = /24 하나. 칸에는 다음 홉의 번호를 넣습니다.
  2. /24 이하 프리픽스를 추가하면 그 프리픽스가 덮는 모든 칸에 번호를 씁니다. /16 하나 = 256칸, /8 하나 = 65,536칸.
  3. 짧은 프리픽스가 긴 프리픽스를 덮어쓰지 않게 합니다. 쓴 뒤에 그 범위 안의 더 긴 프리픽스를 짧은 순서로 다시 씁니다. 그래서 각 칸에는 가장 긴 일치가 남습니다.
  4. 조회는 한 줄입니다: self.hops[self.first[address >> 8]]
  5. /24보다 긴 프리픽스는 길이별 dict에 두고 먼저 확인합니다. 이 벤치마크에는 없습니다.

하드웨어는 왜 트라이를 쓰는가
  • 트라이는 최악에도 32단계로 제한됩니다. 각 단계를 파이프라인의 한 단계로 만들어 클록마다 조회 하나를 끝냅니다.
  • 트라이의 메모리는 항목 수에 비례합니다. DIR-24-8은 항목 수와 관계없이 64 MB입니다.
  • 파이썬에서는 결과가 반대입니다. 배열이나 dict 접근 한 번은 C 코드 한 번입니다. 32비트 순회는 인터프리터 반복 32번입니다.

3.9DHCP

개념

DHCP는 호스트가 네트워크에 들어올 때 주소, 서브넷 마스크, 기본 게이트웨이, DNS 서버 주소를 자동으로 줍니다. UDP를 쓰며 서버는 67번, 클라이언트는 68번 포트입니다.

출발지가 0.0.0.0인 이유

클라이언트는 아직 주소가 없습니다. 다른 값을 넣을 수 없습니다.

목적지가 255.255.255.255인 이유

서버가 누구인지(있는지도) 모릅니다. 모두에게 보내야 합니다.

Ack가 유니캐스트일 수 있는 이유

이제 서버가 클라이언트의 MAC(chaddr)과 줄 주소(yiaddr)를 압니다.

임대(lease)의 시간표

이 프로젝트에서 · Task 2 Part C
  1. 핫스팟의 기억된 임대를 지웠습니다. 그렇지 않으면 Discover/Offer 없이 Request/Ack만 보입니다.
  2. Wi-Fi를 다시 연결하는 동안 port 67 or port 68로 캡처했습니다.
  3. #3–#6에 DORA 네 개가 모두 있습니다 (C1).
  4. 캠퍼스 응답(#2)은 172.16.0.7에서 왔지만 서버 식별자는 192.168.98.23였습니다. DHCP 서버가 다른 서브넷에 있고 라우터가 릴레이(relay)했다는 증거입니다.

3.10NAT

개념

NAT(Network Address Translation)는 내부망의 여러 호스트가 공인 주소 하나를 공유하게 합니다. 포트 번호로 연결을 구분합니다.

쓰는 이유

IPv4 주소 부족. 내부 주소를 바꿔도 외부에 알릴 필요 없음. ISP를 바꿔도 내부는 그대로.

깨뜨리는 것 ①

라우터가 전송 계층의 포트를 바꿉니다. 계층 원칙을 어깁니다.

깨뜨리는 것 ②

외부에서 먼저 시작하는 연결: 표에 항목이 없어 어느 내부 호스트인지 모릅니다. P2P에는 릴레이나 NAT 통과가 필요합니다.

NAT가 두 겹일 때: CGNAT

노트북10.53.36.69→ NAT ① 휴대폰핫스팟→ 휴대폰 셀룰러 주소100.64.x 또는 사설? (확인 못 함)→ NAT ② 통신사?CGNAT→ 공인 주소118.235.95.xxx (KT)
절차 · NAT 겹수 세기
  1. 노트북의 인터페이스 주소를 읽으십시오.
  2. 외부 서버가 본 공인 주소를 확인하십시오 (api.ipify.org).
  3. 두 주소가 다르면 NAT가 최소 한 겹 있습니다.
  4. 공유기 또는 휴대폰의 외부 쪽 인터페이스 주소를 읽으십시오.
  5. 그 주소가 사설 또는 100.64.0.0/10이고 공인 주소와 다르면 NAT가 두 겹입니다.
traceroute로는 셀 수 없습니다

traceroute는 사설 주소가 쓰인 곳을 보여 줍니다. 변환이 일어난 곳을 보여 주지 않습니다. 캠퍼스 경로에도 NAT 없이 사설 홉(192.168.98.132, 10.x)이 있었습니다.

203.0.113.64/26의 첫 사용 가능 주소, 마지막 사용 가능 주소, 브로드캐스트는?

/26은 호스트 비트 6개, 블록 크기 64입니다. 네트워크 .64, 첫 주소 .65, 마지막 주소 .126, 브로드캐스트 .127입니다.

163.152.6.5/24를 parse_cidr가 거부하는 이유는?

호스트 비트(마지막 8비트)가 0이 아닙니다. 이것은 네트워크가 아니라 그 네트워크 안의 호스트 하나입니다.

0.0.0.0/0이 다른 항목에 항상 지는 이유는?

프리픽스 길이가 0으로 가장 짧습니다. LPM은 가장 긴 일치를 고르므로 다른 일치가 하나라도 있으면 집니다.

기본 게이트웨이가 반드시 같은 서브넷에 있어야 하는 이유는?

호스트는 서브넷 밖으로 갈 패킷을 게이트웨이에게 링크 계층으로 직접 보냅니다. 서브넷 밖에 있으면 직접 보낼 수 없습니다.

DIR-24-8의 조회 시간은 무엇에 비례합니까?

테이블 크기와 무관하게 일정합니다(배열 읽기 1번). 대가는 항목 수와 무관한 64 MB 메모리와 느린 추가입니다.

DHCP Discover의 출발지와 목적지는? 왜 그래야 합니까?

0.0.0.0 → 255.255.255.255. 클라이언트는 자기 주소도 서버 주소도 모르기 때문입니다.

NAT가 두 겹인지 확인하려면 어느 주소를 읽어야 합니까?

공유기·휴대폰의 외부 쪽 인터페이스 주소입니다. 그것이 사설이나 100.64/10이고 공인 주소와 다르면 두 겹입니다.
